# Design: `report-bugs-to-clickup` skill

**Date:** 2026-09-01
**Author:** Julia Disarli (julia.disarli@otonomi.ai)
**Status:** Approved

> ⚠️ **Superseded in part:** the ticket-destination model described in §5 below was corrected on 2026-09-01 — see `2026-09-01-report-improvements-to-clickup-design.md` Part 1 for the fix. Tickets are created in a **fixed project List** (asked from the user), and separately **associated** to the active Sprint List via `clickup_add_task_to_list` — the sprint list is never the ticket's creation destination. The rest of this document (title/description format, confirmation gate, severity handling, etc.) is unaffected and still accurate.

## Purpose

Automate the creation of ClickUp bug tickets from a `qa-report.md` file
generated by the `qa-agent` module (or any QA session using the same
report format), so that a QA engineer does not have to manually
transcribe each row of the report's "Bug Register" table into ClickUp.

## Trigger

Manual, on-demand. This is a project skill invoked explicitly by the
user:

```
/report-bugs-to-clickup <path-to-qa-report.md>
```

It is **not** wired into the automatic end-of-session flow of
`qa-agent`. Rationale:

- Editorial control: the user can review/adjust severities or discard
  false positives in the report before any ClickUp ticket is created.
- Decoupling: `qa-agent` has no ClickUp MCP configured and is focused
  purely on testing/reporting. Ticket creation is a separate concern
  with a separate MCP, run from this repo (`qa-team`), where the
  ClickUp MCP is available.
- Reusability: the skill can target any `qa-report.md`, from any
  project/client (e.g. QA-Otonomi, QA-Catalyst), not only a report
  just generated in the current session.

## Location

`qa-team/.claude/skills/report-bugs-to-clickup/SKILL.md` — a
project-level skill in this repo (not inside `qa-agent/`, which has no
ClickUp MCP configured).

## Input

A path to a `qa-report.md` file following the format defined in
`qa-agent/CLAUDE.md`'s "Report Format" section, notably the **Bug
Register** table:

```markdown
## Bug Register
| ID | Severity | Description | Evidence |
|----|----------|-------------|----------|
| BUG-001 | 🔴 High / 🟡 Medium / 🟢 Low | ... | screenshot.png |
```

Plus the report header (`# QA Report — {Tested flow}`, `**URL:**`,
`**Date:**`) and the evidence folder path convention (see
`qa-agent/CLAUDE.md` § "Evidence Structure") to recover hostname and
subpath.

## Flow

### 1. Parse the report

Read the Bug Register table (ID, Severity, Description, Evidence) and
the report header (URL, date, tested flow name). If the table is
missing or has no rows, stop and tell the user — do not create
anything.

### 2. Infer per-bug / per-report metadata

- **Platform**: default `Web`. `Mobile` if the report's viewport is
  375×667 only or the tested flow name mentions "Mobile App".
- **Environment**: inferred from the hostname in the report's URL —
  `localhost` / `staging.*` → `Staging`; anything else recognized as
  a production domain → `Production`; otherwise `Dev`.
- **Page/Flow**: from the evidence folder subpath segment (e.g.
  `root` → `Home`, `register` → `Register`, `users-profile` → `Users
  Profile`), using a small technical-name → readable-name mapping.

These three are computed once per report (all bugs in one report
share the same URL/flow/environment) unless the report covers a full
site audit with multiple pages, in which case Page/Flow is
recalculated per finding based on which page section of the report it
came from.

### 3. Build ticket title

```
[BUG] {Platform} | {Environment} | {Page} | {Short description}
```

Example: `[BUG] Web | Staging | Home | The user cannot see the image`

`{Short description}` is the Bug Register `Description` column,
trimmed to a concise phrase (title-length, not the full sentence if
the original is long).

### 4. Build ticket description

Fixed template (matches the user's existing ClickUp bug template):

```
Preconditions:
-

Steps to reproduce:
-

Actual Result:
{Description column verbatim}

Expected result:
-

Additional information:
Original ID: {BUG-XXX from report}
Severity: {High|Medium|Low}
URL: {full URL from report}
Evidence: {path/filename from Evidence column}
Reported by: {QA display name} (auto-filled, see step 6)
```

`Preconditions`, `Steps to reproduce`, and `Expected result` are left
as empty template placeholders — the skill does not fabricate details
the report doesn't contain. The user or assignee fills these in
ClickUp afterward if needed.

### 5. Locate the active sprint (for later association)

Ask the user which ClickUp Space/Folder holds the project's Sprints
(e.g. "Otonomi > Sprints"). Use
`clickup_get_workspace_hierarchy` to list the Lists inside that
Folder. Each sprint List has start/end dates; the skill treats the
List whose date range includes today's date as the "Current Sprint"
and stores it for later association with created tickets (via
`clickup_add_task_to_list` in step 9).

If no List's date range covers today (gap between sprints, or dates
not set), tell the user and ask them to pick the sprint List
manually from the ones shown.

### 6. Identify the reporting QA

Resolve the currently authenticated ClickUp user (via the ClickUp MCP
identity/workspace-members lookup) to get their display name and
user ID. This user is used as the **assignee** for every ticket
created in this run, and their name is also written into the
"Additional information" section of the description (step 4).

### 7. Environment tag

Every ticket created gets a tag matching the inferred Environment
(`staging`, `production`, or `dev`), added via
`clickup_add_tag_to_task` right after creation (or as part of the
create call if the ClickUp MCP task-creation tool accepts tags
directly).

### 8. Confirmation before creating anything

Before calling any ClickUp write operation, show the user a table
with, for every bug found in the report:

| Title | Severity | Destination (List) | Sprint | Tag | Assignee |

Wait for explicit confirmation. If the user asks for changes (e.g.
drop a row, edit a title), apply them and re-show the table before
proceeding.

### 9. Create tickets

For every row in the Bug Register (all severities — High, Medium,
Low; no filtering), in order:

1. `clickup_create_task` in the fixed project List (as configured
   by the user), with the built title and description, and the
   assignee set to the current QA user.
2. `clickup_add_task_to_list` to associate the created ticket with
   the active Sprint List (found in step 5).
3. `clickup_add_tag_to_task` with the environment tag.
4. If the Evidence column names a screenshot file that exists on
   disk next to the report, attach it via
   `clickup_attach_task_file` / `clickup_request_attachment_upload`.

A failure on any individual step for one bug (e.g. attachment upload
fails) does not abort the batch — the skill continues with the
remaining bugs and reports the failure at the end.

### 10. Final report

Print a summary: for each bug, the ClickUp task URL if created
successfully, or the error if it failed. No silent failures.

## Error handling

- Report file not found, or no "Bug Register" section / no rows →
  stop, tell the user, create nothing.
- No sprint List's date range covers today → ask the user to pick a
  destination List manually (do not guess).
- Individual ticket creation/attachment/tag failure → continue with
  the rest of the batch, surface the failure in the final report.
- ClickUp MCP not connected / tools unavailable → stop immediately
  with a clear message, same pattern as `qa-agent`'s Playwright MCP
  pre-flight check.

## Out of scope (for this iteration)

- Auto-triggering from `qa-agent`'s end-of-session flow.
- Filtering by severity (all severities are created as tickets).
- Editing/syncing existing ClickUp tickets on a re-run (each run
  creates new tickets; no dedupe against previously created ones).
- Custom fields beyond tag + assignee (e.g. a dedicated ClickUp
  "Severity" custom field) — can be added later if the target List
  has one configured.
